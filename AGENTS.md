## What this repo is

PixelXpert is an Android module for Google Pixel stock firmware. It is a single
APK that plays two roles:

1. A normal app — Compose UI, preference storage, root access, updater.
2. A code-injection module — loaded by libxposed into other processes
   (SystemUI, system server, Pixel Launcher, Settings, Dialer, Telecom) where it
   hooks framework methods to add features.

Package: `sh.siava.pixelxpert`. Modules: `:app`, `:modPackProcessor`,
`:buildSrc`. Language: Kotlin. UI: Jetpack Compose + Navigation 3. DI: Koin.
Hooks: libxposed API 102.

## Hard rules

Violating any of these produces a change that compiles and silently does nothing.

1. **A pack's target comes from its annotations, not its folder.**
   `modpacks/systemui/IconPacks.kt` is `@SettingsModPack`. Always read the
   annotations.

   A class may carry **more than one** target annotation, and that is the
   intended way to serve several processes from one implementation. Three packs
   do it today: `IconPacks` (`@SystemUIModPack` + `@SettingsModPack`),
   `BrightnessRange` and `StatusbarSize` (`@SystemUIModPack` +
   `@FrameworkModPack`). `ModPackProcessor` iterates per annotation, so a
   dual-annotated class emits one registry row per target and is constructed
   separately in each matching process. It is not a mistake to be "fixed".

2. **Preference keys are a cross-process string contract.**
   The app writes the key; the hooked process reads it by the same literal. A
   typo compiles clean and returns the default forever. Grep both sides.

3. **Never hand-write the mod pack registry.**
   `sh.siava.pixelxpert.xposed.ModPacks` is generated by `:modPackProcessor` into
   `app/build/generated/ksp/`. If a new pack does not run, inspect that generated
   file before debugging anything else.

4. **All hooks go through `XposedRuntime`.**
   It is the only bridge to libxposed. A second hook engine loses generation
   tracking, and `retire()` will leave hooks running.

5. **Hot reload state must be classloader-neutral.**
   Only strings, primitives and framework objects (context, class loaders,
   resources, application info). Holding module objects keeps the retired
   generation alive.

6. **Release resources in `onUnloaded()`.**
   Threads, sockets, receivers, listeners. Hooks are handled by the framework;
   everything else is yours.

7. **Do not block system server's main thread on the preference provider.**
   `XPLauncher` deliberately runs that wait on a tracked background thread.
   Blocking main hangs boot.

8. **Do not edit generated files, `version.properties` bumps, or release
   manifests by hand** unless you are deliberately performing a release. CI owns
   those.

9. **Tab indentation, LF endings, max line 120.** See `.editorconfig`. The
   project is ktlint `intellij_idea` style.

## Toolchain status in this checkout

There is **no JDK, no Android SDK, and no Gradle cache** on this machine.
`java -version` fails and `./gradlew` cannot run.

You can still read, search, and write code. You **cannot** compile, lint, or run
tests locally. Say so explicitly rather than claiming a change is verified.

To make builds work: install JDK 21, Android SDK platform 37, and set
`ANDROID_HOME`. Full instructions in `docs/guides/build-locally.md`.

Build facts: `compileSdk=37`, `minSdk=37`, `targetSdk=37`, `abiFilters` is
`arm64-v8a` only, AGP 9.1.0, Kotlin 2.2.21, Gradle 9.3.1.

## Verification protocol

There are no unit tests in this repository. Verification is by inspection and,
where available, by build.

Before you claim a change is complete:

1. **Grep the key strings.** If you touched a preference, confirm the literal
   appears identically in `ui/` and `xposed/`.
2. **Confirm the annotation.** If you added a pack, confirm it carries the target
   annotation(s) for every process it should run in.
3. **Trace the release path.** If you acquired a resource, confirm `onUnloaded`
   releases it.
4. **State your confidence honestly.** "Written but not compiled — no JDK on this
   machine" is a correct and expected report. Do not describe uncompiled code as
   working.

## Documentation rules

If you add or change documentation under `docs/`, follow
`docs/agent/DOC_STYLE.md`. It is a contract, not a suggestion. In particular:

- Facts and file paths, not adjectives.
- Every claim must be checkable against source you actually read.
- Every doc is linked from `docs/README.md`.
- No emoji, no marketing language.
- Machine-readable companions under `docs/reference/data/` must stay in sync
  with their Markdown tables in the same commit.

Run `node scripts/check-docs.mjs` before committing documentation. It verifies
that internal links resolve and that every referenced path exists.

## Git and remotes

| Remote | URL | Role |
| --- | --- | --- |
| `origin` | `https://github.com/Codecity001/PixelXpert` | Upstream, read-only for us |
| `fork` | `https://github.com/omegas-super/PixelXpert` | Our fork, push here |

Working branch is `canary`. Push documentation and tooling to `fork`. Do not push
to `origin`.

Sync upstream changes with:

```bash
git fetch origin
git merge origin/canary
```

The `docs/guides/release-process.md` and `scripts/sync-fork.sh` cover the full
fork workflow. The complete procedure is in `docs/guides/fork-workflow.md`.

**CI write-back hazard:** the canary release workflow commits version bumps back
to `canary` after a release. If you hold local commits on `canary` when a release
runs, your next push will be rejected. Rebase before pushing.

## Anti-patterns observed in this codebase

These exist in the source. Do not extend them, and do not assume they are
correct just because they are present.

- Silent `catch` blocks that swallow hook failures. Useful for robustness, fatal
  for debugging. When adding one, log first.
- Silent fallback to debug signing when `ReleaseKey.properties` is absent
  (`app/build.gradle.kts`). A release build can produce a debug-signed APK with no
  warning.
- The `CONTRIBUTING.md` at the repo root is four lines and predates `docs/`. Treat
  `docs/` as authoritative.
