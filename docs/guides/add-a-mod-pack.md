# Add a Mod Pack

How to add a feature that hooks a framework or app method: pick the target
annotation, extend `XposedModPack`, read the preference, install the hook, and
verify it actually ran. Written as a procedure with a worked example copied from
a real pack.

**Audience:** agent or contributor adding a hooking feature
**Prereqs:** [overview](../architecture/overview.md),
[mod pack lifecycle](../architecture/modpack-lifecycle.md),
[reflection and hooks](../architecture/reflection-and-hooks.md),
[preferences system](../architecture/preferences-system.md)

---

## Summary

- A mod pack is a Kotlin class extending `XposedModPack`, annotated with one or
  more target annotations, with a single-argument `Context` constructor.
- `:modPackProcessor` (KSP) discovers annotated classes at build time and emits
  `sh.siava.pixelxpert.xposed.ModPacks`. Never hand-write that table.
- `XPLauncher.loadModPacks` matches the generated row's `targetPackage` against
  the hooked process's package name, and its `childProcessName` against the
  process name.
- The pack reads preferences in `onPreferenceUpdated` and installs hooks in
  `onPackageLoaded`. Nothing else runs on its own.
- The most common failure is a pack that compiles, registers, loads, and does
  nothing. Every failure mode in this guide produces that same symptom.

## Model

### The base class

`app/src/main/java/sh/siava/pixelxpert/xposed/XposedModPack.kt`:

```kotlin
abstract class XposedModPack(context: Context) : Logger() {
	@JvmField
	protected val mContext: Context = context

	abstract fun onPreferenceUpdated(vararg key: String?)

	@Throws(Throwable::class)
	abstract fun onPackageLoaded(PRParam: XposedModuleInterface.PackageReadyParam)

	open fun onUnloaded() { }
	// saveHotReloadState / restoreHotReloadState and their protected hooks
}
```

`extends Logger()` is what puts a bare `log(...)` in scope inside every pack.

Call order, from `XPLauncher.loadModPack`:

1. `thisClass.getConstructor(Context::class.java).newInstance(mContext)`
2. `modInstance.onPreferenceUpdated()` with no keys, inside
   `try { } catch (ignored: Throwable) { }`
3. `modInstance.onPackageLoaded(param)`
4. `modInstance.restoreHotReloadState(saved)` if a hot reload carried state
5. `runningMods.add(modInstance)` and
   `XposedRuntime.generation?.registerCleanup { modInstance.onUnloaded() }`

The whole of steps 1 to 5 is inside one `try`. A throw logs
`"Start Error Dump - Occurred in " + thisClass.name` and the pack simply is not
in `runningMods`.

### Target annotations

`app/src/main/java/sh/siava/pixelxpert/xposed/annotations/` holds seven target
annotations. Each is itself annotated with `@BaseModPack(targetPackage = ...)`,
which is what the processor scans for.

| Annotation | Target package constant | Value |
| --- | --- | --- |
| `@SystemUIModPack` | `Constants.SYSTEM_UI_PACKAGE` | `com.android.systemui` |
| `@FrameworkModPack` | `Constants.SYSTEM_FRAMEWORK_PACKAGE` | `android` |
| `@LauncherModPack` | `Constants.LAUNCHER_PACKAGE` | `com.google.android.apps.nexuslauncher` |
| `@SettingsModPack` | `Constants.SETTINGS_PACKAGE` | `com.android.settings` |
| `@DialerModPack` | `Constants.DIALER_PACKAGE` | `com.google.android.dialer` |
| `@TelecomServerModPack` | `Constants.TELECOM_SERVER_PACKAGE` | `com.android.server.telecom` |
| `@CommonModPack` | `""` | every scoped package |

A class may carry more than one target annotation, and that is the intended way to
serve several processes from one implementation. `IconPacks.kt` carries
`@SystemUIModPack` and `@SettingsModPack`; `BrightnessRange.kt` and
`StatusbarSize.kt` each carry `@FrameworkModPack` and `@SystemUIModPack`. The
processor iterates per annotation, so a dual-annotated class emits one registry
row per target and is constructed separately in each matching process. Do not
"fix" a dual-annotated class down to one annotation.

Three modifier annotations live in `app/src/main/java/sh/siava/pixelxpert/annotations/`:

| Annotation | Effect on the generated row |
| --- | --- |
| `@ModPackPriority(priority = n)` | Sort key; default is `99`, lower loads first |
| `@ChildProcessModPack(processNameContains = "s")` | `childProcess = true`, `childProcessName = "s"` |
| `@MainProcessModPack` | Forces `targetsMainProcess = true` even when a child marker is present |

The processor's rule for `targetsMainProcess`:

```kotlin
targetsMainProcess = childProcessName == null || pack.has(MAIN_PROCESS_ANNOTATION),
```

So a pack with no `@ChildProcessModPack` is main-process-only, and adding
`@MainProcessModPack` widens a child-process pack back to the main process.

### The generated table

`modPackProcessor/src/main/kotlin/sh/siava/pixelxpert/registry/ModPackProcessor.kt`
emits `sh.siava.pixelxpert.xposed.ModPacks` into
`app/build/generated/ksp/`. The emitted shape is:

```kotlin
// Generated by :modPackProcessor. Do not edit.
package sh.siava.pixelxpert.xposed

import sh.siava.pixelxpert.annotations.ModPackData

object ModPacks {
	fun getModPacks(): List<ModPackData> = listOf(
		ModPackData(<Class>::class.java, "<targetPackage>", <targetsMainProcess>, <childProcess>, "<childProcessName>"),
	)
}
```

Rows are sorted by `priority`, then `targetPackage`, then `className`. An empty
result is a hard error: `logger.error("ModPackProcessor discovered no mod packs;
refusing to emit an empty registry")`.

`ModPackData` is in `app/src/main/java/sh/siava/pixelxpert/annotations/ModPackData.kt`
and also exposes `targetsMainProcess` / `targetsChildProcess` aliases.

### Process matching

`XPLauncher.loadModPacks`, verbatim:

```kotlin
for (modPackData in ModPacks.getModPacks()) {
	val partOfProcessName = if (modPackData.targetsMainProcess) "" else modPackData.childProcessName

	val target = modPackData.targetPackage
	val matchesTarget = target == param.packageName ||
		target.isEmpty() ||
		(target == Constants.SYSTEM_FRAMEWORK_PACKAGE && isSystemServer)

	if (matchesTarget && processName.contains(partOfProcessName)) {
		loadModPack(modPackData.clazz as Class<out XposedModPack>, param)
	}
}
```

Three consequences worth memorising:

- `target.isEmpty()` is the `@CommonModPack` case: it matches every package.
- The framework target matches `isSystemServer`, not the literal package name.
- A main-process pack gets `partOfProcessName = ""`, and
  `processName.contains("")` is always true, so the second test never filters it.

### The hook DSL

`ReflectedClass.of(name)` / `ofIfPossible(name)` resolve a class through the
default class loader and then the framework class loader. Both may return a
`ReflectedClass` whose `clazz` is `null`; `before`/`after` then return an empty
handle set instead of throwing. That is what lets one pack target several
firmware builds.

The two calls a pack makes:

```kotlin
ReflectedClass.of("com.example.Target")
	.before("methodName")
	.run { param -> /* param.args, param.thisObject, param.setResult(...) */ }

ReflectedClass.of("com.example.Target")
	.after("methodName")
	.run { param -> /* param.result is the real return value */ }
```

`RunParam` (in `app/src/main/java/sh/siava/pixelxpert/xposed/utils/reflection/HookHelper.kt`)
exposes `thisObject`, `method`, `args`, `setResult(x)`, `getResult<T>()`,
`getThisObject<T>()`, `getArg<T>(i)`.

Setting a result in a `before` hook skips `proceed`:
`if (param.isResultSet) param.result else chain.proceed(param.args)`.

## Walkthrough

### 1. Choose the target process

Decide which process must be inside for the hook to fire, then pick the matching
annotation. Read the existing packs in that folder for the package layout this
firmware actually ships; class names move between Android releases.

The folder does not decide the target. `modpacks/systemui/IconPacks.kt` is
`@SystemUIModPack` **and** `@SettingsModPack`; `modpacks/android/ScreenRotation.kt`
hooks `com.android.server.wm.DisplayRotation` from the `android` package.

### 2. Create the file under `xposed/modpacks/<target>/`

Name the file after the class. The package must be
`sh.siava.pixelxpert.xposed.modpacks.<target>`; the folder name is a convention
only, but keep it consistent with its siblings.

### 3. Add the preference on the app side first

A pack reads keys that already exist. Follow
[add-a-preference](add-a-preference.md) first if the feature needs a new toggle.
Writing the pack first is legal but leaves the key unwritten on every device, so
the reader's fallback literal becomes the permanent value and the feature cannot
be turned off.

### 4. Write the class

A complete minimal pack, mirroring
`app/src/main/java/sh/siava/pixelxpert/xposed/modpacks/android/ScreenRotation.kt`:

```kotlin
package sh.siava.pixelxpert.xposed.modpacks.android

import android.content.Context
import io.github.libxposed.api.XposedModuleInterface
import sh.siava.pixelxpert.xposed.XPrefs.Xprefs
import sh.siava.pixelxpert.xposed.XposedModPack
import sh.siava.pixelxpert.xposed.annotations.FrameworkModPack
import sh.siava.pixelxpert.xposed.utils.reflection.ReflectedClass

@FrameworkModPack
class ScreenRotation(context: Context) : XposedModPack(context) {

	companion object {
		private const val USER_ROTATION_LOCKED = 1

		private var allScreenRotations = false
	}

	override fun onPreferenceUpdated(vararg key: String?) {
		allScreenRotations = Xprefs.getBoolean("allScreenRotations", false)
	}

	override fun onPackageLoaded(PRParam: XposedModuleInterface.PackageReadyParam) {
		try {
			val DisplayRotationClass = ReflectedClass.of("com.android.server.wm.DisplayRotation")

			DisplayRotationClass
				.before("rotationForOrientation")
				.run { param ->
					try {
						if (!allScreenRotations) return@run
						// ... read args, setResult ...
					} catch (ignored: Throwable) {
					}
				}
		} catch (ignored: Exception) {
		}
	}
}
```

Five properties of that shape are worth copying deliberately:

1. The state is a `companion object` field, or a private instance field when it
   must survive a hook that fires before `onPackageLoaded`. `CaffeineTile` keeps
   its tile handle and wake lock as instance fields; `ScreenRotation`,
   `ScreenRecord`, `FingerprintWhileDozing`, `HotSpotController` and
   `FeatureFlagsMods` all keep their flags in a `companion object`.
2. `onPreferenceUpdated` reads **every** key the pack uses, unconditionally, not
   only the one named in `key`. That is what makes the initial no-key call seed
   the whole state.
3. The hook body re-checks the flag on every invocation
   (`if (!allScreenRotations) return@run`). Hooks stay installed; the flag is the
   gate.
4. The class name is resolved once, in `onPackageLoaded`, not per invocation.
5. The failure path is a swallowed `Throwable`. That is the house style and it is
   also the reason a broken pack is invisible — see the failure table.

### 5. Verify the annotation is picked up

There is no local build on this machine (no JDK, no Android SDK). On a machine
that can build, `:app` declares two build types, `release` and `debug`, and no
flavours, so the KSP task is one of:

```bash
./gradlew :app:kspDebugKotlin
grep -n "YourPackClassName" app/build/generated/ksp/debug/kotlin/sh/siava/pixelxpert/xposed/ModPacks.kt
```

The row must appear with the expected target package. If it does not, the
annotation is wrong, the class is not under the module's source set, or the
processor ran before the file existed. `:app` wires the processor with
`ksp(project(":modPackProcessor"))` in `app/build.gradle.kts`.

### 6. Confirm the pack loaded on device

The framework log carries one line per load, from `XPLauncher.waitForXprefsLoad`:

```text
Loading PixelXpert version: <version> on <packageName>
```

and a failure line from `loadModPack`:

```text
Start Error Dump - Occurred in <fully.qualified.PackClassName>
```

The Hooks page (`Route.Hooks`, tab Hooks) reports per-package
`HOOKED` / `NOT_ENABLED` / `NO_RESPONSE` by broadcasting
`Constants.ACTION_CHECK_XPOSED_ENABLED` and waiting five seconds. It answers the
question "is the module in this process at all", not "did my pack's hook fire".

### 7. Confirm the hook fired

Add a temporary `log(...)` inside the hook body and a `log(...)` at the end of
`onPackageLoaded`. `Logger.log` routes to the framework log and falls back to
logcat. Remove the per-invocation log before merging: `ReflectedClass`'s
`maybeLogHook` is gated on `FLAG_DEBUG_HOOKS = false` for the same reason.

### 8. Release anything you acquired

`onUnloaded()` is called from a generation cleanup. `CaffeineTile` is the
reference: it unregisters its screen-off receiver, cancels its
`CountDownTimer`, releases its `PowerManager.WakeLock` and drops its tile
reference. `HookTester` unregisters its broadcast receiver. Hooks are handled by
the framework and must **not** be unhooked there.

## Contracts

| Rule | Reason |
| --- | --- |
| Carry a target annotation for every process the feature must run in, and no others | Each annotation emits its own registry row, so an extra one constructs a second instance that resolves nothing |
| The class has a public `(Context)` constructor | `getConstructor(Context::class.java).newInstance(mContext)` |
| Every preference key is a literal that exists on the app side | The reader's fallback silently wins otherwise |
| The fallback literal equals the node's declared `default` | Otherwise the switch shows one thing and the feature does another |
| Read preferences only in `onPreferenceUpdated` | `onPackageLoaded` runs once and is not replayed on change |
| Resolve classes in `onPackageLoaded`, gate behaviour on flags inside the hook | A remote read is a binder call; a per-invocation read costs latency |
| Release threads, receivers, timers, wake locks in `onUnloaded` | Generation cleanups are the only release point |
| Hot reload state may hold framework objects only | Module objects keep the retired generation alive |
| Do not hand-write `ModPacks.kt` | It is regenerated on every build |
| Do not call `XPrefs.release()` from a pack | It is a generation cleanup owned by `XPLauncher` |

## Failure modes

Every row below produces the same observable result: the feature does nothing,
no exception reaches the user, and the app does not crash. That shared symptom is
why this table is the most useful page in the guide.

| Mistake | Why it is silent | How to detect it |
| --- | --- | --- |
| **Wrong annotation** — `@SystemUIModPack` on a class whose hook target lives in `android` | The pack registers in SystemUI, resolves the class to `null` via `of()`/`ofIfPossible()`, and `before`/`after` return an empty handle set instead of throwing | The generated `ModPacks.kt` row names `com.android.systemui` while the hook target's package is `android` |
| **Wrong annotation kind** — `@CommonModPack` where a specific package was meant | It registers in all six processes; five of them resolve nothing and the sixth may not be the one you tested | `ModPacks.kt` row shows `targetPackage = ""` |
| **Package mismatch** — the class resolves but its `before("x")` finds no method | `HookHelper.hookAllMethods` iterates `clazz.declaredMethods.filter { it.name == name }`; an empty list yields an empty handle set, no log, no throw | `FLAG_DEBUG_HOOKS` is `false`, so even the size log is off; add a temporary log in `onPackageLoaded` |
| **Child-process marker wrong** — `@ChildProcessModPack(processNameContains = "screenshot")` on a pack that must also run in the main process | `targetsMainProcess` becomes `false`, `partOfProcessName` becomes `"screenshot"`, and the main process's name does not contain it | Compare with `ScreenshotManager`, which documents running in both; add `@MainProcessModPack` to widen it |
| **Child-process marker empty string** — `@ChildProcessModPack(processNameContains = "")` without `@MainProcessModPack` | `processName.contains("")` is true everywhere, so the pack loads in every process of the package, including ones where its hook target is absent | `CallVibrator` pairs `""` with `@MainProcessModPack` deliberately; without the pair the intent is unreadable |
| **Preference key typo** — `Xprefs.getBoolean("allScreenRotation", false)` | `RemotePreferences` returns the passed default for an absent key; nothing compares keys | `grep -r "allScreenRotation" app/src/main/java` shows one hit instead of two |
| **Hook target missing on this firmware** — the class was renamed or removed | `ReflectedClass.of` returns a null-clazz wrapper and every `before`/`after` is a no-op by design | Use `dumpStructure()` on a resolved class, or compare against `xposed/inspector/*` output; `HookAuditScreen` reports `PRESENT`/`ABSENT`/`INLINED` per target |
| **Exception swallowed by the pack loader** — a throw in the constructor or in `onPackageLoaded` | `loadModPack` catches `Throwable`, logs `"Start Error Dump - Occurred in <class>"` and never adds the pack to `runningMods` | The log line is the only signal; there is no UI surface for it |
| **Exception swallowed in `onPreferenceUpdated`** | `loadModPack` wraps the first call in `try { } catch (ignored: Throwable) { }`, so a throwing reader leaves the pack's flags at their Kotlin field initialisers | The pack loads and hooks correctly but reads all-default values forever |
| **Exception swallowed inside the hook body** — the house-style `catch (ignored: Throwable) { }` | The hook runs, throws, and the catch eats it; the framework's own behaviour proceeds unmodified | Log before catching; `AGENTS.md` lists silent catches as a known anti-pattern |
| **State read only in `onPackageLoaded`** | The value is correct at load and stale forever after | Toggle the setting and check the feature does not react |
| **Pack never registered** — no target annotation at all | The processor emits nothing for it; if no pack at all is found it fails the build with `refusing to emit an empty registry` | `ModPacks.kt` has no row for the class |
| **Pack registered but never matched** — the target package is not in the module's LSPosed scope | `XPLauncher.loadModPacks` only compares against the package that got a `PackageReadyParam`; an out-of-scope package never gets one | The Hooks page iterates `R.array.module_scope` in `app/src/main/res/values/xp_module_scope.xml` (five entries) and marks each row `NOT_ENABLED` when `XposedService.scope` does not contain it |
| **Bootloop protector skipped the package** | `onXPrefsReady` returns before `loadModPacks` when `isBootLooped(packageName)` is true | Log line `"PixelXpert: Possible bootloop in <pkg>. Will not load for now"`; the Hooks page shows `BOOTLOOPED` at three strikes |
| **Preferences provider unreachable** | `waitForXprefsLoad` loops forever and no pack is constructed in that process | The `Loading PixelXpert version:` line never appears |
| **Hook installed on the wrong overload** | `before("name")` hooks every declared method of that name; a per-overload guard that never matches leaves all of them passing through | `ScreenRecord` guards on `(param.method as Method).parameterCount == 8` |

## Checklist

- [ ] The file is at `app/src/main/java/sh/siava/pixelxpert/xposed/modpacks/<target>/<Name>.kt`
- [ ] The class extends `XposedModPack(context)` and has one `(Context)` constructor
- [ ] It carries exactly the target annotations the feature needs, read from the
      annotation file, not inferred from the folder
- [ ] Every preference key it reads exists in a `PrefScreen` node, spelled
      identically
- [ ] Every fallback literal equals the node's declared `default`
- [ ] `onPreferenceUpdated` reads all of its keys, unconditionally
- [ ] Hooks are installed in `onPackageLoaded` and gated on flags inside the body
- [ ] Every acquired thread, receiver, timer, wake lock is released in `onUnloaded`
- [ ] Any state saved for hot reload is a framework object, a string, or a primitive
- [ ] A temporary log proves the hook fired, and has been removed
- [ ] `docs/reference/modpack-catalog.md` and its JSON companion are updated in
      the same commit
