# Mod Pack Lifecycle

How a mod pack class is discovered at build time, emitted into the generated
registry, constructed at runtime, called, and unloaded. Read this before adding a
pack or debugging one that never runs.

**Audience:** agent adding a pack, or debugging "my pack does nothing"
**Prereqs:** [overview](overview.md), [xposed-runtime](xposed-runtime.md)

---

## Summary

- A pack is any class extending `XposedModPack` that carries a target annotation
  from `app/src/main/java/sh/siava/pixelxpert/xposed/annotations/`.
- Each of those annotations is itself annotated `@BaseModPack(targetPackage = …)`,
  which is the hook the KSP processor searches for.
- `:modPackProcessor` emits `sh.siava.pixelxpert.xposed.ModPacks` with one
  `ModPackData` row per (annotation, pack) pair, sorted by priority.
- `XPLauncher.loadModPacks` walks that list and matches on target package plus
  process name.
- Load order is the order of the generated list. `@ModPackPriority` is applied by
  the generator's sort, not carried into the runtime row.
- `onPreferenceUpdated()` fires once before `onPackageLoaded()`, so a pack can
  seed state without a null check.

---

## Model

### The annotation set

Two layers. The meta-annotations live in
`app/src/main/java/sh/siava/pixelxpert/annotations/`; the target annotations live
in `app/src/main/java/sh/siava/pixelxpert/xposed/annotations/`.

| Annotation | File | Applies to | Meaning |
| --- | --- | --- | --- |
| `@BaseModPack(targetPackage)` | `annotations/BaseModPack.kt` | annotation classes | "classes annotated with me belong to `targetPackage`" |
| `@ChildProcessModPack(processNameContains)` | `annotations/ChildProcessModPack.kt` | pack classes | restricts the pack to processes whose name contains the marker |
| `@MainProcessModPack` | `annotations/MainProcessModPack.kt` | pack classes | forces `targetsMainProcess = true` |
| `@ModPackPriority(priority = 99)` | `annotations/ModPackPriority.kt` | pack classes | load order; lower runs first |
| `ModPackData` | `annotations/ModPackData.kt` | data class | one registry row |

The seven target annotations:

| Annotation | Target package | Source |
| --- | --- | --- |
| `@SystemUIModPack` | `com.android.systemui` | `Constants.SYSTEM_UI_PACKAGE` |
| `@FrameworkModPack` | `android` | `Constants.SYSTEM_FRAMEWORK_PACKAGE` |
| `@LauncherModPack` | `com.google.android.apps.nexuslauncher` | `Constants.LAUNCHER_PACKAGE` |
| `@SettingsModPack` | `com.android.settings` | `Constants.SETTINGS_PACKAGE` |
| `@DialerModPack` | `com.google.android.dialer` | `Constants.DIALER_PACKAGE` |
| `@TelecomServerModPack` | `com.android.server.telecom` | `Constants.TELECOM_SERVER_PACKAGE` |
| `@CommonModPack` | `""` (empty) | literal in `CommonModPack.kt` |

All seven are `@Retention(AnnotationRetention.SOURCE)` and
`@Target(AnnotationTarget.CLASS)`. Source retention is why nothing can read them
at runtime: the registry is the only consumer, and it is generated.

### How the processor resolves a row

`modPackProcessor/src/main/kotlin/sh/siava/pixelxpert/registry/ModPackProcessor.kt`
does the resolution in one pass:

```kotlin
val metas = resolver.getSymbolsWithAnnotation(BASE_ANNOTATION).toList()
for (meta in metas) {
	val declaration = meta as? KSClassDeclaration ?: continue
	val qualified = declaration.qualifiedName?.asString() ?: continue
	val targetPackage = declaration.annotationValue("BaseModPack", "targetPackage") as? String
	val candidates = resolver.getSymbolsWithAnnotation(qualified).toList()
	for (candidate in candidates) { ... rows += Row(...) }
}
```

Three consequences an agent must know:

1. **A pack may carry more than one target annotation.** The outer loop runs once
   per annotation, and each run collects the classes carrying it. A class with
   two target annotations produces two rows. `IconPacks` is annotated
   `@SystemUIModPack` *and* `@SettingsModPack`, so it loads in both processes —
   that is how one class serves two targets. Note that this contradicts the
   "exactly one target annotation" phrasing in `AGENTS.md`; the source is the
   authority here.
2. **`targetPackage` may be null**, in which case the processor warns
   (`"<class> has @BaseModPack without a targetPackage"`) and registers the pack
   with an empty target — which matches every package. A typo in a
   `@BaseModPack(targetPackage = …)` therefore widens a pack instead of disabling
   it.
3. **Discovery is by annotation, never by directory.** `modpacks/systemui/IconPacks.kt`
   targets Settings as well as SystemUI; `modpacks/MiscSettings.kt` sits at the
   package root and targets SystemUI.

### What the processor emits

`writeModPacks` writes a single file, `package
sh.siava.pixelxpert.xposed`, class name `ModPacks`:

```kotlin
// Generated by :modPackProcessor. Do not edit.
package sh.siava.pixelxpert.xposed

import sh.siava.pixelxpert.annotations.ModPackData

object ModPacks {
	fun getModPacks(): List<ModPackData> = listOf(
		ModPackData(<class>::class.java, "<targetPackage>", <targetsMainProcess>, <childProcess != null>, "<childProcessName>"),
	)
}
```

The five positional arguments map onto
`ModPackData(clazz, targetPackage, mainProcess, childProcess, childProcessName)`.

Two properties of the emitted file matter:

- **`priority` is not emitted.** The `Row` carries it, and `rows.sortWith` uses
  it, but the constructor call has no slot for it. Load order is therefore
  *baked into the list order* by the generator. `@ModPackPriority(priority = 1)`
  works because `compareBy<Row> { it.priority }` puts those rows first, not
  because anything reads the annotation at runtime. The KDoc on
  `BatteryDataProvider` and `ThermalProvider` describes the intent correctly, but
  the mechanism is the sort.
- **Ties are broken deterministically**: `.thenBy { it.targetPackage }
  .thenBy { it.className }`. Two packs at the default priority 99 load in
  alphabetical order of target package, then class name.

The sort and the escape helper are worth knowing when reading the output:

```kotlin
rows.sortWith(compareBy<Row> { it.priority }.thenBy { it.targetPackage }.thenBy { it.className })
```

`String.escape()` escapes `\`, `"`, `\n`, `\r`, `\t` and `$`. Without the `$`
escape, a class name containing a dollar sign (a nested class) would emit a
string template instead of a literal.

### Empty registry is a hard failure

```kotlin
if (rows.isEmpty()) {
	logger.error("ModPackProcessor discovered no mod packs; refusing to emit an empty registry")
}
```

The processor logs an error rather than emitting an empty `ModPacks`. It still
emits the file, so the build produces a `ModPacks` whose list is empty and every
pack silently stops running. Treat that log line as a build failure.

`process` also short-circuits with a `generated` flag, so a second KSP round does
not emit a duplicate file.

### The base class

`app/src/main/java/sh/siava/pixelxpert/xposed/XposedModPack.kt`:

```kotlin
abstract class XposedModPack(context: Context) : Logger() {
	@JvmField
	protected val mContext: Context = context

	abstract fun onPreferenceUpdated(vararg key: String?)
	abstract fun onPackageLoaded(PRParam: XposedModuleInterface.PackageReadyParam)
	open fun onUnloaded() {}
	// saveHotReloadState / restoreHotReloadState wrap:
	protected open fun onSaveHotReloadState(outState: MutableMap<String, Any?>) {}
	protected open fun onRestoreHotReloadState(savedState: Map<String, Any?>) {}
}
```

`extends Logger` is not decoration: it puts a bare `log(...)` in scope inside
every pack, which is why pack bodies call `log("...")` with no receiver. `Logger`
itself is `open class Logger` with a companion holding `@JvmStatic fun log`.

`mContext` is `protected`, not private, so a pack reads the hooked process's
context directly.

## Walkthrough

### Build time

1. KSP runs `ModPackProcessorProvider.create` →
   `ModPackProcessor(codeGenerator, logger)`.
2. `process(resolver)` returns immediately if `generated` is already true.
3. It collects every class annotated `@BaseModPack` — that is, the seven target
   annotation classes.
4. For each, it reads `targetPackage` and then collects every class annotated
   with that annotation.
5. For each such class it builds a `Row` with `className`, `targetPackage`,
   `priority` (from `@ModPackPriority`, else `99`), `childProcessName` (from
   `@ChildProcessModPack`), and
   `targetsMainProcess = childProcessName == null || pack.has(MAIN_PROCESS_ANNOTATION)`.
6. It sorts, then writes `ModPacks.kt` under `app/build/generated/ksp/`.

### Runtime

1. `XPLauncher.loadModPacks` calls `ModPacks.getModPacks()`.
2. For each `ModPackData` it computes `partOfProcessName` and `matchesTarget`
   exactly as described in [xposed-runtime](xposed-runtime.md#process-targeting).
3. Matching rows go to `loadModPack(thisClass, param)`.
4. `loadModPack` constructs the pack reflectively:
   `thisClass.getConstructor(Context::class.java).newInstance(mContext)`.
5. It calls `onPreferenceUpdated()` — no arguments, so the pack's own
   `key.isNotEmpty()` branch is skipped and it takes the "load everything" path.
   The call is wrapped in a `try { } catch (ignored: Throwable) { }`, so a
   failure here is invisible.
6. It calls `onPackageLoaded(param)`.
7. If `pendingPackStates` has an entry keyed by this class's name (a hot reload),
   it calls `restoreHotReloadState`. A failure logs
   `PixelXpert: could not restore hot reload state for <class>`.
8. It appends the instance to `XPLauncher.runningMods` and registers
   `onUnloaded()` as a generation cleanup.

Everything from step 4 is inside one `try` whose catch logs
`Start Error Dump - Occurred in <class>` followed by the throwable. A pack that
throws in its constructor is skipped and the rest still load.

### Unload

`onUnloaded()` runs from `XposedGeneration.retire()`, which iterates
`cleanups.asReversed()`. Because `registerGenerationCleanups` ran first, the
order at retire time is: pack `onUnloaded`s (in reverse registration order, so
last-loaded unloads first), then `unbindRootService()`, then
`SystemUtils.release()`, then `XPrefs.release()`.

A cleanup that throws is caught and logged as `Generation cleanup failed`, so one
bad `onUnloaded` cannot stop the others.

## Contracts

- **The class must extend `XposedModPack` and take exactly one `Context`
  constructor parameter.** `loadModPack` reflects
  `getConstructor(Context::class.java)`. Anything else throws and the pack is
  skipped with `Start Error Dump`.
- **The class must carry at least one target annotation.** Without one it never
  appears in `ModPacks` and never runs. There is no runtime fallback scan.
- **`onPreferenceUpdated` must tolerate being called with no arguments.** That is
  the first call a pack ever receives.
- **`onPreferenceUpdated` must not assume `key[0]` is non-null.** `XPrefs.loadEverything`
  can pass a null key through; `MiscSettings` uses `key[0]!!` deliberately to
  preserve the original Java `switch` throw.
- **`onUnloaded` must release every resource the pack acquired.** Hooks are the
  framework's; threads, receivers, wake locks, `CountDownTimer`s and view
  listeners are the pack's. 15 of the 56 pack files implement it; the other 41
  acquire nothing that outlives them, or leak.
- **Never hand-write or edit `ModPacks.kt`.** It is regenerated on every build.
- **Do not infer the target from the directory.** Read the annotation.
- **A pack that hooks nothing is legal.** `MiscSettings.onPackageLoaded` is empty;
  the pack exists only as a preference-change sink. `HookTester` and
  `HookAuditor` are pure broadcast receivers.

## Failure modes

| Symptom | Cause in code | Fix |
| --- | --- | --- |
| Pack compiles, never runs, no log line | Not in `ModPacks`: missing target annotation, or the class does not extend `XposedModPack` | Inspect `app/build/generated/ksp/.../ModPacks.kt` before anything else |
| `ModPackProcessor discovered no mod packs; refusing to emit an empty registry` | The `@BaseModPack` meta-annotations were removed or the processor is not registered in `META-INF/services` | Check `modPackProcessor/src/main/resources/META-INF/services/com.google.devtools.ksp.processing.SymbolProcessorProvider` |
| `<class> has @BaseModPack without a targetPackage` (KSP warning) | `@BaseModPack` on a target annotation has no `targetPackage` | Add it; an empty target matches every package |
| Pack runs in every process instead of one | `targetPackage` resolved to `""`, or the annotation is `@CommonModPack` | Check the annotation's `@BaseModPack(targetPackage = …)` argument |
| `Start Error Dump - Occurred in <class>` | Constructor signature wrong, or `onPreferenceUpdated`/`onPackageLoaded` threw | Read the trace on the following log line |
| Pack runs but a preference never reaches it | The pack ignores the key in its `when (key[0])` branch and only reads on the empty-key path | Confirm `onPreferenceUpdated` re-reads unconditionally, as `GestureNavbarManager` does |
| `@ModPackPriority` appears to have no effect between two packs | Both are at the same priority, so alphabetical tie-break decided | Give them distinct priorities |
| A dual-target pack hooks a process you did not intend | Two rows exist and both matched, so the class is constructed once per process | Decide deliberately: `IconPacks` is `@SystemUIModPack` plus `@SettingsModPack` and hooks `Resources.getDrawable`, which both processes call — it does not branch on process name |

## Checklist

Before adding a pack:

- [ ] Class extends `XposedModPack(context: Context)` with exactly that signature
- [ ] Exactly the target annotation(s) you intend — two annotations means two
      rows and two loads
- [ ] `onPreferenceUpdated` reads every key unconditionally, before the
      `if (key.isNotEmpty())` branch
- [ ] `onPackageLoaded` installs hooks via `ReflectedClass`, not a second engine
- [ ] `onUnloaded` releases anything long-lived
- [ ] Rebuild and confirm the class appears in the generated `ModPacks.kt`
- [ ] Confirm the generated row's `targetPackage` string matches a real package
- [ ] If load order matters, set `@ModPackPriority` and confirm the row is early
      in the generated list
